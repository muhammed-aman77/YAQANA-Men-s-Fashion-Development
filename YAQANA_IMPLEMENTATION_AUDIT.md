# YAQANA Admin Platform Repository Audit

**Audit scope:** Source and configuration inspection of the React/Vite frontend and `yaqana-backend`. This document includes the original source-audit snapshot and a dated continuation addendum below; later changes are identified separately.

## Architecture observed

- `frontend/` is a React 18 and Vite application. `/admin` renders `AdminDashboardPage` through `AdminRoute`; the storefront shell (navigation, cart drawer, footer, search, intro splash) is excluded on admin routes.
- The admin experience is concentrated in `frontend/src/pages/AdminDashboardPage.jsx` and admin-specific styles in `frontend/src/index.css`. It uses existing service helpers in `frontend/src/services/api.js` and admin utility modules.
- `yaqana-backend/` is an Express 5 API using Mongoose. Route modules connect controllers to MongoDB models; `src/app.js` mounts API groups and shared middleware.
- Local development startup is pinned to the loopback `yaqana_local_dev_20261115` database. `npm start` uses the required `MONGODB_URI`. The project README describes a proposed dedicated `yaqana_staging` Atlas database but says staging has not been deployed or tested; actual hosted configuration is external and unknown.
- Product documents embed size-colour variants, SKU/stock, colour images, and product images. Category is stored on products as a name string; collection is stored as `collectionName`. `Category` and `Collection` are independent documents, not product ObjectId references.
- Order checkout stores integer paise, adjusts stock, records stock movement, creates the order, and clears the cart inside a MongoDB transaction. Transaction-dependent operations require a replica set or sharded deployment.
- Uploads validate file type/signature and size, then use Cloudinary or local disk according to environment configuration. Existing `/images/`, `/uploads/`, and external image references are retained.
- The user model supports `customer`, `support_agent`, `admin`, and `owner`, with server-side administrator checks, permission definitions, append-only-style `AdminAudit` records and staff permission endpoints. A secure Owner bootstrap/transfer API and full transaction-backed role administration remain incomplete.

## Classification and recommended work

- **No storefront changes required:** Preserve the existing customer-facing route tree, components, styles, authentication consumers, cart, checkout, and product rendering.
- **Reuse without replacement:** Existing catalog APIs/models, money conversion, variant validation, upload storage, auth/CSRF, order transitions, inventory adjustment service, support ticket module, and admin utility tests.
- **Remaining Level 1 order:** (1) The current-state backup/restore gate is complete. Obtain authorized Windows Administrator access for the local replica-set configuration, then verify inventory/checkout transaction commit and rollback only on disposable fixtures. (2) Verify receipt stock application and transaction-backed receiving. (3) Implement the already-documented server-enforced staff roles, controlled Owner bootstrap/transfer, append-only audit controls, and notification foundation only after explicit account/authorization decisions and transaction prerequisites. (4) Complete order search/detail/timeline/fulfilment and safe COD workflow after COD business rules are approved. (5) Specify and implement returns/exchanges/refund ledger and duplicate-refund protection after refund rules/payment evidence are approved. (6) Complete premium operational features—global search, activity/action center, saved filters, audited bulk actions—and permission/PII tests. (7) Run a final Level 1 acceptance matrix against behavior, persistence, authorization, responsiveness, and tests.
- **Missing or incomplete APIs/models:** staff permission and Owner bootstrap/transfer/audit APIs/models; notification model/API; COD lifecycle/reconciliation; return/exchange/refund ledger; order search/detail/timeline/fulfilment APIs; policy editing (Owner-only until bootstrap); and saved-filter/activity services.
- **Missing verification:** transaction commit/rollback; database-backed SKU reservation and concurrent adjustment/receipt tests; live approval/receipt consistency; owner/admin/restricted-role permission tests; authenticated admin browser flow with real credentials; real Cloudinary upload/deletion; and hosted Vercel/Render health/build/deployment verification.
- **Needs explicit business/operator input:** eligible account and authorization for Owner bootstrap; high-risk approval rules beyond the currently implemented inventory thresholds; COD confirmation/collection/reconciliation; return eligibility/inspection/refund evidence; payment-provider behavior; and supplier/cost/tax/coupon policies.

## Continuation addendum — 2026-11-21

- The original findings above are a historical implementation audit, not a complete current-state pass claim. Subsequent implementation added staff-role/permission foundations, `AdminAudit`, Cloudinary asset deletion, return/refund request records, support/contact ticket integration, and the isolated demo catalogue; these remain partial or externally/transaction-gated as described in the current progress and known-issues reports.
- SKU lifecycle had no inventory-row Restore control or restore API. A new admin-only SKU Restore endpoint now activates only an inactive or discontinued variant and records the actor, reason, product, SKU, size, colour, and before/after lifecycle state in `AdminAudit` within the same MongoDB transaction. It does not change stock, cost, SKU identity, or product publication status. The inventory API exposes whether the connected topology supports transactions; the UI disables Restore when it does not.
- The approved local demo data was inspected read-only: 18 demo products, 180 unique SKUs, 169 active, 5 inactive, and 6 discontinued; no duplicate SKU values. The separate legacy catalogue remains 24 development samples and 370 aggregate units; no SKU or stock was changed by this inspection.
- Latest automated verification is recorded in `YAQANA_TESTING_REPORT.md`. MongoDB remains standalone, so the Restore mutation itself and its persistence/audit behavior have only been verified with service tests, not against a transaction-capable database.
- **Overall status remains NOT READY FOR MANUAL GIT PUSH.** Transaction commit/rollback, checkout/reservation/receipt stock lifecycle, secure Owner bootstrap, complete COD/order/refund workflows, hosted deployment configuration, and live provider operations remain incomplete or unverified.

## Orders discovery continuation — 2026-11-21

- The admin Orders page now supports server-driven search across order ID/visible reference suffix and customer name, email, or phone; combined order-status, payment-status, COD/prepaid, and inclusive UTC date filters; bounded page sizes and pagination; and responsive loading, error, and empty states.
- The backend preserves the existing response envelope and caps page size at 100. Invalid status/payment/date filters return explicit HTTP 400 responses. Existing per-order status transitions and mutation safeguards are unchanged.
- Controller tests exercise the real `GET /api/orders` handler over an in-process HTTP server with Mongoose model doubles. This is API/controller-level evidence, not a live authenticated request against the local database.
- Orders discovery is complete as a read-only Level 1 slice. Dedicated order details/timeline, fulfilment/shipment integrations, database-backed authenticated verification, and transaction-dependent order mutations remain outstanding. Overall status remains **NOT READY FOR MANUAL GIT PUSH**.
